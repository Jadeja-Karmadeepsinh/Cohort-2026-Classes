Absolutely. In Mongoose, when you write:

```js
const userSchema = new mongoose.Schema({
  name: {
    type: String,
    required: true,
    trim: true,
    minlength: 3,
    maxlength: 50
  }
});
```

there are **two different things** you should separate in your mind:

1. **Schema types** → `String`, `Number`, `Boolean`, `Date`, `ObjectId`, etc.
2. **SchemaType options** → `required`, `default`, `unique`, `trim`, `minlength`, `maxlength`, `min`, `max`, `enum`, etc.

---

# 1. Mongoose Schema Types

These are the main types you'll use.

| Type         | Example           | Used for                   |
| ------------ | ----------------- | -------------------------- |
| `String`     | `"Karma"`         | Names, emails, titles      |
| `Number`     | `25`              | Age, runs, price           |
| `Boolean`    | `true`            | Active/inactive            |
| `Date`       | `new Date()`      | DOB, createdAt             |
| `ObjectId`   | `ObjectId(...)`   | References to documents    |
| `Array`      | `["bat", "ball"]` | Lists                      |
| `Map`        | `Map`             | Key-value data             |
| `Buffer`     | binary data       | Raw binary                 |
| `Decimal128` | `12.50`           | High-precision decimals    |
| `Mixed`      | anything          | Flexible/unstructured data |

For your IPL project, you'll probably use mainly:

```js
String
Number
Boolean
Date
ObjectId
Array
```

---

# 2. String options

This is where options like `trim`, `minlength`, etc. come in.

### `required`

Field must exist.

```js
name: {
  type: String,
  required: true
}
```

You can also provide a custom message:

```js
name: {
  type: String,
  required: [true, "Name is required"]
}
```

---

### `trim`

Removes whitespace from the beginning and end.

```js
name: {
  type: String,
  trim: true
}
```

Input:

```text
"   Karmadeepsinh   "
```

Stored as:

```text
"Karmadeepsinh"
```

**Important:** `trim` doesn't remove spaces inside the string.

```text
"Kar ma"
```

stays:

```text
"Kar ma"
```

---

### `lowercase`

Automatically converts the string to lowercase.

```js
email: {
  type: String,
  lowercase: true
}
```

Input:

```text
KARMA@GMAIL.COM
```

Stored:

```text
karma@gmail.com
```

---

### `uppercase`

Opposite of `lowercase`.

```js
country: {
  type: String,
  uppercase: true
}
```

---

### `minlength`

Minimum number of characters.

```js
username: {
  type: String,
  minlength: 3
}
```

`"ab"` → ❌

`"abc"` → ✅

Custom message:

```js
username: {
  type: String,
  minlength: [3, "Username must be at least 3 characters"]
}
```

---

### `maxlength`

Maximum number of characters.

```js
username: {
  type: String,
  maxlength: [30, "Username cannot exceed 30 characters"]
}
```

---

### `enum`

Only specific values are allowed.

This is **extremely useful for your IPL project**.

```js
role: {
  type: String,
  enum: ["user", "admin"],
  default: "user"
}
```

So:

```text
"user"  ✅
"admin" ✅
"manager" ❌
"hello" ❌
```

You can also provide a custom message:

```js
role: {
  type: String,
  enum: {
    values: ["user", "admin"],
    message: "Invalid role"
  }
}
```

---

### `match`

Validates a string against a regular expression.

Very useful for emails, usernames, etc.

```js
email: {
  type: String,
  match: /^[^\s@]+@[^\s@]+\.[^\s@]+$/
}
```

---

### `validate`

For completely custom validation.

```js
username: {
  type: String,
  validate: {
    validator: function(value) {
      return !value.includes(" ");
    },
    message: "Username cannot contain spaces"
  }
}
```

This is useful when built-in options aren't enough.

---

# 3. Number options

For numbers you have:

### `min`

```js
age: {
  type: Number,
  min: 18
}
```

`17` → ❌

`18` → ✅

Custom message:

```js
age: {
  type: Number,
  min: [18, "Age must be at least 18"]
}
```

---

### `max`

```js
age: {
  type: Number,
  max: 100
}
```

---

### `enum`

Numbers can also use `enum`.

```js
jerseyNumber: {
  type: Number,
  enum: [7, 10, 18, 45]
}
```

---

### `default`

Works with numbers too.

```js
runs: {
  type: Number,
  default: 0
}
```

---

# 4. Date options

For example:

```js
dob: {
  type: Date,
  required: true
}
```

You can use:

### `min`

```js
dob: {
  type: Date,
  min: new Date("1900-01-01")
}
```

### `max`

```js
dob: {
  type: Date,
  max: new Date()
}
```

This can be useful for your player model.

---

# 5. ObjectId

This is particularly important for your IPL project.

Suppose:

```js
const playerSchema = new mongoose.Schema({
  name: String,

  team: {
    type: mongoose.Schema.Types.ObjectId,
    ref: "Team"
  }
});
```

Now:

```text
Player
   │
   │ team
   ▼
Team document
```

You can then:

```js
Player.find().populate("team")
```

This is the **reference + populate** concept you were asking about earlier.

---

# 6. Arrays

You can define:

```js
skills: {
  type: [String]
}
```

Then:

```json
{
  "skills": ["Batting", "Bowling"]
}
```

You can also write:

```js
skills: [String]
```

---

### Array of ObjectIds

Very useful in your IPL system.

```js
players: [{
  type: mongoose.Schema.Types.ObjectId,
  ref: "Player"
}]
```

Conceptually:

```text
Team
 │
 ├── Player ID
 ├── Player ID
 └── Player ID
```

# 7. `default`

This is one of the most important options.

```js
role: {
  type: String,
  default: "user"
}
```

If the user doesn't provide `role`:

```json
{
  "name": "Karma"
}
```

Mongoose creates:

```json
{
  "name": "Karma",
  "role": "user"
}
```

This is exactly what you should use for your IPL authentication system.

---

# 8. `unique`

You'll see this a lot:

```js
email: {
  type: String,
  unique: true
}
```

This means duplicate emails shouldn't be allowed.

But there's an **important misconception**:

> `unique` is **not a validator**.

It tells MongoDB/Mongoose to create a **unique index**.

So don't think:

```text
unique = validation
```

Think:

```text
unique = database index constraint
```

For example:

```text
karma@gmail.com   ✅
karma@gmail.com   ❌
```

---

# 9. `index`

You can explicitly create an index:

```js
email: {
  type: String,
  index: true
}
```

Useful when you frequently search by that field.

For example:

```js
Player.find({ name: "Virat Kohli" })
```

If you're frequently searching players by name, an index might help.

---

# 10. `immutable`

This is an interesting one.

```js
createdAt: {
  type: Date,
  immutable: true
}
```

Once set, it shouldn't be changed through normal Mongoose updates.

Useful for things like:

```text
createdAt
```

where you don't want someone changing the original creation date.

---

# 11. `alias`

You can give a field another name in your Mongoose model.

```js
name: {
  type: String,
  alias: "playerName"
}
```

This is less commonly needed in beginner projects, but it exists.

---

# 12. `select`

Controls whether a field is selected by default.

This is **very useful for passwords**.

```js
password: {
  type: String,
  required: true,
  select: false
}
```

Now:

```js
User.find()
```

won't normally include the password.

When you actually need it for login:

```js
User.findOne({ email }).select("+password")
```

This is a very good pattern for your auth module.

---

# 13. `get` and `set`

Mongoose also allows custom getters/setters.

For example:

```js
name: {
  type: String,
  set: value => value.trim()
}
```

Although for simple transformations you should generally use built-ins such as:

```js
trim: true
lowercase: true
uppercase: true
```

---

# 14. `timestamps`

This one is slightly different.

Instead of:

```js
createdAt: ...
updatedAt: ...
```

you can do:

```js
const userSchema = new mongoose.Schema(
  {
    name: String,
    email: String
  },
  {
    timestamps: true
  }
);
```

Mongoose automatically creates:

```text
createdAt
updatedAt
```

and updates `updatedAt` when the document changes.

**Very useful.**

---

# 15. Schema-level options

There are also options that aren't attached to individual fields.

For example:

```js
const userSchema = new mongoose.Schema(
  {
    name: String,
    email: String
  },
  {
    timestamps: true
  }
);
```

Other schema-level things you'll encounter include:

```text
timestamps
strict
versionKey
collection
toJSON
toObject
minimize
_id
```

You don't need to memorize all of these right now.

---

# 16. A realistic User schema

Putting several of these together:

```js
const userSchema = new mongoose.Schema(
  {
    name: {
      type: String,
      required: [true, "Name is required"],
      trim: true,
      minlength: [3, "Name must be at least 3 characters"],
      maxlength: [50, "Name cannot exceed 50 characters"]
    },

    email: {
      type: String,
      required: [true, "Email is required"],
      trim: true,
      lowercase: true,
      unique: true
    },

    password: {
      type: String,
      required: [true, "Password is required"],
      minlength: [8, "Password must be at least 8 characters"],
      select: false
    },

    role: {
      type: String,
      enum: ["user", "admin"],
      default: "user"
    }
  },
  {
    timestamps: true
  }
);
```

This one schema demonstrates a **large portion of the options you'll actually use**.

# 🧠 The easiest way to remember them

Don't try to memorize a giant list.

When you're defining a field, ask these questions:

```text
                    FIELD
                      │
       ┌──────────────┼──────────────┐
       │              │              │
     WHAT?          REQUIRED?      DEFAULT?
       │              │              │
    String          required       default
    Number
    Date
    ObjectId
       │
       ▼
   RESTRICTIONS?
       │
   ┌───┼────┬──────┐
   │   │    │      │
  min max enum   match
  minlength
  maxlength
       │
       ▼
   TRANSFORM?
       │
   ┌───┼───────┐
   │   │       │
 trim lowercase uppercase
       │
       ▼
   DATABASE?
       │
   ┌───┼────────┐
   │   │        │
 unique index  select
```
