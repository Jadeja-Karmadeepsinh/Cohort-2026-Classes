The key thing you were missing is:

> **`client_id` and `redirect_uri` do NOT come from nowhere. The client application gets them when it registers itself with your Authorization Server.**

# 4. The most important distinction

## OAuth 2.0

OAuth answers:

> "Can this application access this user's resources?"

You get:

```text
access_token
```

## OpenID Connect

OIDC answers:

> "Who is this user?"

You get:

```text
id_token
```

So:

```text
OAuth 2.0
    ↓
Access Token
    ↓
Authorization

OIDC
    ↓
ID Token
    ↓
Authentication / Identity
```

OIDC Authorization Code flow returns an authorization code first, which is exchanged at the token endpoint for an ID token and access token. ([OpenID Foundation][2])

# 8. Authorization code model

Never immediately give the client an access token after login.

First generate a short-lived authorization code.

```js
import mongoose from "mongoose";

const authorizationCodeSchema = new mongoose.Schema(
    {
        codeHash: {
            type: String,
            required: true,
            unique: true
        },

        clientId: {
            type: String,
            required: true,
            index: true
        },

        userId: {
            type: mongoose.Schema.Types.ObjectId,
            required: true
        },

        redirectUri: {
            type: String,
            required: true
        },

        scope: {
            type: String,
            required: true
        },

        nonce: {
            type: String
        },

        codeChallenge: {
            type: String
        },

        codeChallengeMethod: {
            type: String
        },

        expiresAt: {
            type: Date,
            required: true
        },

        used: {
            type: Boolean,
            default: false
```

# 14. `/o/authorize`

Your authorization endpoint receives:

```js
app.get("/o/authorize", async (req, res) => {

    const {
        client_id,
        redirect_uri,
        response_type,
        scope,
        state,
        nonce,
        code_challenge,
        code_challenge_method
    } = req.query;

    if (response_type !== "code") {
        return res.status(400).json({
            error: "unsupported_response_type"
        });
    }

    const client = await Client.findOne({
        clientId: client_id
    });

    if (!client) {
        return res.status(400).json({
            error: "invalid_client"
        });
    }

    if (!client.redirectUris.includes(redirect_uri)) {
        return res.status(400).json({
            error: "invalid_redirect_uri"
        });
    }

    const requestedScopes =
        scope?.split(" ") ?? [];

    for (const requestedScope of requestedScopes) {

        if (!client.allowedScopes.includes(requestedScope)) {

            return res.status(400).json({
                error: "invalid_scope"
            });

        }
    }

    // Store the authorization request temporarily
    // so login can resume after authentication.

    const params = new URLSearchParams({
        client_id,
        redirect_uri,
        response_type,
        scope,
        state: state ?? "",
        nonce: nonce ?? "",
        ...(code_challenge
            ? { code_challenge }
            : {}),
        ...(code_challenge_method
            ? { code_challenge_method }
            : {})
    });

    return res.redirect(
        `/o/authenticate?${params.toString()}`
    );
});
```

Notice the important security check:

```js
client.redirectUris.includes(redirect_uri)
```

You **never** blindly trust:

```text
redirect_uri
```

from the browser.

# 18. Client calls `/o/token`

SportsIN receives:

```text
code=abc123
```

and sends:

```http
POST /o/token
```

with:

```json
{
    "grant_type": "authorization_code",
    "code": "abc123",
    "client_id": "cli_7f4c9d2a",
    "client_secret": "secret",
    "redirect_uri": "http://localhost:3000/auth/callback"
}
```

Your server:

```js
app.post("/o/token", async (req, res) => {

    const {
        grant_type,
        code,
        client_id,
        client_secret,
        redirect_uri
    } = req.body;

    if (grant_type !== "authorization_code") {
        return res.status(400).json({
            error: "unsupported_grant_type"
        });
    }

    const client = await findAndValidateClient(
        client_id,
        client_secret
    );

    if (!client) {
        return res.status(401).json({
            error: "invalid_client"
        });
    }

    const codeHash =
        crypto
            .createHash("sha256")
            .update(code)
            .digest("hex");

    const authorizationCode =
        await AuthorizationCode.findOne({
            codeHash,
            clientId: client_id
        });

    if (!authorizationCode) {
        return res.status(400).json({
            error: "invalid_grant"
        });
    }

    if (authorizationCode.used) {
        return res.status(400).json({
            error: "invalid_grant"
        });
    }

    if (
        authorizationCode.expiresAt <
        new Date()
    ) {
        return res.status(400).json({
            error: "invalid_grant"
        });
    }

    if (
        authorizationCode.redirectUri !==
        redirect_uri
    ) {
        return res.status(400).json({
            error: "invalid_grant"
        });
    }

    authorizationCode.used = true;

    await authorizationCode.save();

    // Now generate tokens
});
```

Again, notice:

```js
authorizationCode.redirectUri === redirect_uri
```

The redirect URI used during authorization must match the one used during token exchange. ([RFC Editor][1])

# 22. Where PKCE fits

For a **real modern implementation**, I strongly recommend adding PKCE.

The flow becomes:

```text
Client generates:

code_verifier
      ↓
SHA256
      ↓
code_challenge
```

Authorization request:

```text
/authorize

client_id=...
redirect_uri=...
response_type=code

code_challenge=...
code_challenge_method=S256
```

Server stores:

```text
code_challenge
```

with authorization code.

Then at `/token`, client sends:

```text
code_verifier
```

Server calculates:

```text
SHA256(code_verifier)
```

and compares:

```text
calculated challenge
        ==
stored challenge
```

Only then does it issue tokens.

This prevents someone who steals the authorization code from simply exchanging it.

## The one mental model I want you to keep

Don't think:

```text
"OIDC is some complicated JWT login thing."
```

Think:

```text
CLIENT
   │
   │ "I want this user to log in"
   ▼
AUTHORIZE
   │
   │ user logs in
   ▼
AUTHORIZATION CODE
   │
   │ client exchanges it
   ▼
TOKEN
   │
   ├───────────────┐
   ▼               ▼
ACCESS TOKEN     ID TOKEN
   │               │
   │               │
OAuth             OIDC
authorization     identity
```

And the missing piece that caused all your confusion is:

```text
CLIENT REGISTRATION
       │
       ├── client_id
       ├── client_secret
       └── redirect_uri
```

**That is where `client_id` and `redirect_uri` come from.**

That's also why you should **not hardcode them into your OIDC server**. You store registered clients and validate every authorization request against that registration. That's the real approach described by OAuth/OIDC. ([RFC Editor][1])

If you're building this as a learning project, I'd implement **Authorization Code + PKCE + OIDC ID Token** rather than trying to reproduce every possible OAuth grant. That gives you the core architecture used by modern web applications without dragging you into obsolete flows.
