# 1. First: OAuth vs OIDC

The most important thing to lock into your head:

> **OAuth 2.0 = authorization**
>
> **OIDC = authentication built on top of OAuth 2.0**

Think:

```text
OAuth
User
  ↓
Authorization Server
  ↓
Access Token
  ↓
Client uses protected API
```

OAuth answers:

> "Is this client allowed to access this resource?"

OIDC adds:

```text
OAuth
  +
ID Token
  +
User identity
```

OIDC answers:

> "Who is the user that just authenticated?"

So when you use Google:

```text
Google Authorization Server
        │
        ├── OAuth → Access Token
        │
        └── OIDC → ID Token
```

# 7. `redirect_uri`

This is VERY important.

You said:

> redirect_uri tells Google where to redirect our user after authenticate

Correct.

But later you said:

> token endpoint uses redirect_uri to tell Google where to send access token

❌ **This is wrong.**

The token endpoint does **not** redirect the access token to the redirect URI.

Instead:

### Authorization endpoint

uses:

```text
redirect_uri
```

to redirect the **user's browser** back to the client.

Example:

```text
Google
  ↓
302 Redirect
  ↓
https://photoapp.com/oauth/callback?code=ABC&state=XYZ
```

Then:

```text
PhotoApp backend
      ↓
POST Google token endpoint
      ↓
Access Token + ID Token
```

The token response comes directly in the **HTTP response to the backend**.

There is no browser redirect involved here.

This distinction is extremely important.

# 8. `scope`

You are mostly correct.

Scope represents permissions/claims requested.

For OIDC:

```text
openid
profile
email
```

For OAuth APIs, you can have things like:

```text
photos.read
photos.write
contacts.read
```

So:

```text

```

means approximately:

```text
openid
→ I want OIDC authentication

profile
→ I want basic profile information

email
→ I want email information

photos.read
→ I want permission to read photos
```

### Important

For OIDC, the `openid` scope is what makes the request an **OIDC request** rather than just OAuth.

# 9. `state`

> random string to prevent CSRF attacks


```text

```

Authorization server eventually redirects:


Client checks:

```text

      ==
```

If:


continue.

If:

```text

```

reject.

So `state` basically allows the client to say:

> "I started an authorization request. I expect the response corresponding to THAT request."

It does **not** prove that the response came from Google.

# 18. Access Token vs ID Token

This distinction needs to be absolutely crystal clear.

## Access Token

Used to access a protected resource.

Example:

```http
GET /photos
Authorization: Bearer ACCESS_TOKEN
```

Meaning:

> "I have permission to access photos."

The access token belongs to the **authorization** side.

---

## ID Token

Used to tell the client:

> "This is the user who authenticated."

Example:

```json
{
  "iss": "https://auth.example.com",
  "sub": "user_456",
  "aud": "photo_app_123",
  "exp": 1780000000,
  "iat": 1779996400,
  "name": "John Doe",
  "email": "john@example.com"
}
```

This is OIDC.

---

# 19. Your statement "ID token is JWT"

OIDC defines the ID Token as a **JWT**.

For example:

```text
                    Auth Server

                         │
                         ↓
                   Sign ID Token
                         │
                         ↓
                     ID Token
```

Client receives it.

Client gets your public key from:

```text
/.well-known/jwks.json
```

```text
signature
```


# 25. One more important correction: `nonce`

You included:

```text
nonce
```

but didn't explain it.

`nonce` is an **OIDC-specific value** used to bind the ID Token to the authentication request.

Client generates:

```text
nonce = random_value
```

Authorization request:

```text
nonce=abc123
```

Auth server puts it into the ID Token:

```json
{
  "sub": "user123",
  "aud": "photo-app",
  "nonce": "abc123"
}
```

Client verifies:

```text
ID token nonce
      ==
original nonce
```

So you can think:

```text
state
 ↓
protects authorization response/request correlation

nonce
 ↓
protects/binds the OIDC ID Token to the authentication request

PKCE
 ↓
protects authorization code exchange
```

They solve **different problems**.

# 26. One more correction: claims and scopes

You said:

> name, email, picture if requested in scope

This is directionally right but slightly simplified.

OIDC defines standard scopes such as:

```text
openid
profile
email
address
phone
```

which correspond to standard claims.

For example:

```text
profile
```

can authorize claims such as:

```text
name
family_name
given_name
picture
locale
...
```

and:

```text
email
```

relates to:

```text
email
email_verified
```

But don't think:

```text
scope=profile
```

means:

> "The ID token MUST contain every profile claim."

The exact claims returned depend on the provider's implementation and whether claims are returned in the ID Token, UserInfo response, or otherwise.

For your own implementation, you can choose a clean subset.
