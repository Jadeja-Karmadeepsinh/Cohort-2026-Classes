# 1. First: What problem does OIDC actually solve?

Suppose you have your application:

```text
myapp.com
```

You want users to be able to click:

```text
Login with Google
```

Instead of making your application handle:

```text
username
password
password hashing
password reset
MFA
email verification
login sessions
etc.
```

Google handles the authentication.

Your application basically says:

> "Google, authenticate this person and tell me who they are."

Google says:

> "Sure. This person is user X, their email is [X@example.com](mailto:X@example.com), and I authenticated them."

That is the basic idea behind **OpenID Connect**.

OIDC's core purpose is **authentication + identity information**, built on top of OAuth 2.0. ([OpenID Foundation][1])

---

# 2. OIDC vs OAuth 2.0

This is probably the **single most important distinction** you need to understand.

## OAuth 2.0

OAuth answers:

> **"Can this application access this resource?"**

For example:

```text
Can Spotify access my Google Drive files?
```

or:

```text
Can this application access my Google Calendar?
```

OAuth is primarily about **authorization**.

---

## OIDC

OIDC answers:

> **"Who is this user?"**

For example:

```text
Who logged into my application using Google?
```

So:

```text
OAuth 2.0
    ↓
Authorization
    ↓
"What can this application access?"
```

while:

```text
OIDC
    ↓
Authentication / Identity
    ↓
"Who is this user?"
```

OIDC is an **identity layer on top of OAuth 2.0**. ([OpenID Foundation][2])

---

# 3. The easiest way to remember it

Imagine Google.

### OAuth

You tell Google:

> Give Spotify permission to access my YouTube data.

Google gives Spotify an:

```text
access_token
```

Spotify uses that token to access an API.

---

### OIDC

You tell Google:

> I want to log into Spotify using my Google account.

Google authenticates you and gives Spotify an:

```text
id_token
```

That token contains information about your identity.

For example:

```json
{
  "iss": "https://accounts.google.com",
  "sub": "123456789",
  "aud": "spotify-client-id",
  "email": "user@example.com",
  "email_verified": true
}
```

So:

**access token → access resources**

**ID token → information about authentication/identity**

This distinction is extremely important.

# 7. What is Discovery?

Imagine I tell you:

> "I am an OpenID Provider."

You ask:

> "Okay, but where is your authorization endpoint?"

> "Where is your token endpoint?"

> "Where are your public keys?"

> "Where is your UserInfo endpoint?"

You shouldn't have to manually configure every endpoint.

That's what **OpenID Connect Discovery** helps with.

The client can request:

```http
GET /.well-known/openid-configuration
```

and receive metadata describing the provider and its endpoints. The Discovery specification exists specifically so clients can discover the OpenID Provider and the endpoints needed to interact with it. ([OpenID Foundation][1])

For example:

```json
{
  "issuer": "https://accounts.google.com",
  "authorization_endpoint": "https://accounts.google.com/o/oauth2/v2/auth",
  "userinfo_endpoint": "https://openidconnect.googleapis.com/v1/userinfo",
  "jwks_uri": "https://www.googleapis.com/oauth2/v3/certs"
}
```

That's basically a **directory of the provider's services**.

# 10. Why is it called "authorization" if OIDC is authentication?

Because OIDC is built on OAuth 2.0.

OAuth's authorization endpoint is reused.

OIDC adds authentication semantics to the OAuth flow.

That's why the terminology can initially feel weird.

# 11. Authorization Code

# 13. The three important tokens

You need to understand these extremely well.

## Access Token

Purpose:

> Access protected APIs/resources.

Example:

```text
GET /api/profile
Authorization: Bearer eyJ...
```

The API validates the access token.

---

## ID Token

Purpose:

> Tell the client about the authentication event and the authenticated user.

Usually a JWT.

Example payload:

```json
{
  "iss": "https://accounts.google.com",
  "sub": "123456789",
  "aud": "my-client-id",
  "exp": 1770000000,
  "iat": 1769996400,
  "email": "user@example.com"
}
```

This is **OIDC-specific**.

---

## Refresh Token

Purpose:

> Obtain new access tokens without making the user log in again.

Conceptually:

```text
access token expires
        ↓
refresh token
        ↓
new access token
```

Refresh tokens are part of OAuth flows and can be used with OIDC clients too.

For example:

means:

```text

```

# 17. Symmetric vs asymmetric

You already asked about this.

### Symmetric

Same secret:

```text
Secret
   │
   ├── sign
   │
   └── verify
```

Example:

```text
HS256
```

Both parties need the same secret.

---

### Asymmetric

Two keys:

```text
Private Key
Public Key
```

Private key:

```text
sign
```

Public key:

```text
verify
```

Conceptually:

```text
             OP
             │
       Private Key
             │
             ▼
        sign JWT
             │
             ▼
        Signed JWT
             │
             ▼
           Client
             │
        Public Key
             │
             ▼
        verify JWT
```

This is incredibly useful for OIDC because the provider can keep its private key secret while clients can retrieve the public key.

---

# 18. This is what JWKS is for

You currently have:

```js
router.get('/jwks', (req, res) => {
    return res.json({
        access_key: env.JWT_ACCESS_SECRET,
        refresh_key: env.JWT_REFRESH_SECRET
    })
})
```

That's your **temporary educational implementation**.

Actual JWKS isn't:

```json
{
    "access_key": "secret",
    "refresh_key": "secret"
}
```

Instead, JWKS means:

> **JSON Web Key Set**

It's a JSON document containing public key information.

Conceptually:

```json
{
    "keys": [
        {
            "kty": "RSA",
            "kid": "key-1",
            "use": "sig",
            "alg": "RS256",
            "n": "...",
            "e": "AQAB"
        }
    ]
}
```

The important idea is:

```text
Private key
     ↓
kept secret by OP


Public key
     ↓
published through JWKS
     ↓
clients use it to verify signatures
```

**Never publish the private key.**

---

# 19. Why does JWKS need `kid`?

Imagine you rotate keys.

Today:

```text
private-key-A
public-key-A
```

Tomorrow:

```text
private-key-B
public-key-B
```

Your provider may have both public keys available temporarily.

A JWT can contain:

```json
{
    "kid": "key-B"
}
```

`kid` means:

> Key ID

The verifier sees:

```text
kid = key-B
```

and retrieves the corresponding public key from JWKS.

This becomes important when you learn **key rotation**.

# 27. Redirect URI

This is another **very important** concept.

Suppose your app is:

```text
https://myapp.com
```

After Google finishes authentication, Google needs to know:

> Where should I send the user back?

That's the:

```text
redirect_uri
```

For example:

```text
https://myapp.com/auth/callback
```

Flow:

```text
MyApp
   │
   │ login
   ▼
Google
   │
   │ authenticate
   ▼
https://myapp.com/auth/callback
```

Google must validate that redirect URI.

Otherwise an attacker could try:

```text
redirect_uri=https://evil.com
```

and steal authorization responses.

---

# 28. `state`

Another important security parameter.

The client generates a random value:

```text
state = abc123xyz
```

and sends it during authorization.

After authentication, the provider returns:

```text
state=abc123xyz
```

The client checks:

```text
received state
      ==
original state
```

If not:

```text
REJECT
```

This helps protect against authorization request injection / CSRF-style attacks.

---

# 29. `nonce`

`nonce` is particularly important for OIDC.

The client generates:

```text
nonce = random-value
```

It sends it in the authentication request.

The value is then associated with the ID token.

The client verifies:

```text
ID token nonce
      ==
original nonce
```

This helps prevent replay and token-substitution attacks.

A useful mental distinction:

```text
state
 ↓
protect authorization flow / client request correlation


nonce
 ↓
bind the authentication response/ID token to the original request
```

---

# 30. PKCE

You're almost certainly going to encounter this.

PKCE =

> Proof Key for Code Exchange

It strengthens the authorization-code flow, especially for public clients such as mobile apps and browser applications.

Conceptually:

```text
Client creates:

code_verifier
      ↓
hash it
      ↓
code_challenge
```

The authorization request sends:

```text
code_challenge
```

Later, when exchanging the authorization code:

```text
code_verifier
```

is sent.

The server verifies:

```text
Does verifier produce
the original challenge?
```

If yes:

```text
allow token exchange
```

If no:

```text
reject
```

You'll probably learn:

```text
S256
```

which is the common secure PKCE method.

# 33. How does signature verification work?

Suppose Google signs the ID token using:

```text

```

Google publishes the corresponding public key through:

```text

```

MyApp retrieves:

```text
JWKS
```

```text

  │
  │ private key
  ▼

  │
  ▼
ID Token
  │
  │
  ▼
MyApp
  │
  │ public key from JWKS
  ▼
verify signature
```

This is why your current `/jwks` route is only a placeholder.

# 46. One very important correction about your current project

Your current discovery document:

```js
{
    issuer: ISSUER,
    authorization_endpoint: `${ISSUER}/api/auth/register`,
    userinfo_endpoint: `${ISSUER}/api/auth/me`,
    jwks_uri: `${ISSUER}/api/auth/jwks`,
}
```

is okay **as a learning exercise based on what you've been taught**.

But don't let yourself internalize:

```text
authorization_endpoint = register route
```

as an actual OIDC rule.

It isn't.

Eventually you'll have something more like:

```text
/oauth/authorize
/oauth/token
/oauth/userinfo
/oauth/jwks
```

and those endpoints will participate in a specific protocol flow.

Your:

```text
/api/auth/register
/api/auth/login
/api/auth/me
```

are your application's normal authentication APIs, not inherently OIDC endpoints.

That's one of the most important things I want you to distinguish before your next class.

If you understand those **23 things**, OIDC will stop looking like a giant collection of random endpoints and JSON fields.

It becomes one coherent system:

> **OAuth gives you the authorization framework. OIDC adds a standardized identity/authentication layer on top of it. The provider authenticates the user, issues tokens, and publishes metadata and keys so the client can discover the provider and verify what it receives.** ([OpenID Foundation][1])

And given what you've already learned, **you're actually much closer than you think**. Your biggest missing pieces aren't Express or JWT—they're the **OAuth authorization-code flow, ID tokens, asymmetric signatures/JWKS, and the security parameters (`state`, `nonce`, PKCE)**. Once those click, the OIDC pieces you've already built will make a *lot* more sense.
